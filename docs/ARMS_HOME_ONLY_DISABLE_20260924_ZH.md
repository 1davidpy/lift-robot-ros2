# 短按 X：仅双臂归位后失能

## 本次用户要求

恢复原双臂失能流程：双臂返回 `arms-teleop.json` 的 home，再移除转矩。停用过程中升降保持当前停止高度，不执行 HOME、不返回 0 mm、不发送新高度目标。用户明确选择由现场自行确认碰撞和下落风险，不再把“仅在 0 mm 已确认支撑”推广为任意升降高度均有支撑。

短按 X / 网页归位按钮先撤销底盘、升降运动许可，关闭仍由主机持有的升降会话；确认底盘、升降、双臂停稳，且升降无旧会话后，双臂低速归位。保留夹爪目标。非夹爪关节误差 ≤0.03 rad、速度 ≤0.05 rad/s，连续 0.5 秒稳定后才发送双臂 disable。

这不再要求升降位于 0 mm 或 `home_complete=true`。双臂归位期间仍监控底盘/升降静止、反馈与故障。故障中止归位并保持转矩，不把故障当成移除转矩的命令。B / 网页“停止全部 / 双臂保持”仍立即停止保持，不回位，不移除转矩。

## 本次整机测试的两个停止原因

实测原始记录：`/home/robot/luxi-lift-input-diagnostics-20260924/full_system_test/trace.jsonl`。

1. 前几次 HOME/MOVE 后约 0.7–0.8 秒，协调器因 `base_or_lift_feedback_lost` 停止。当时未记录 CAN 错误，Quest 仍新鲜，升降请求仍在等待最终 ACK。升降状态独立 100 ms 发布，会使协调器继续使用上一条反馈元数据，即使新完整遥测已经抵达。新增立即发布完整反馈状态，保留周期状态更新；没有放宽 500 ms 反馈年龄或其他超时。是否消除现场这类误停仍待验证。
2. 最后一次上行开始后出现真实 CAN ACK-slot 发送错误，TX 错误计数达到 128，发生控制器警告/被动状态通知；升降撤销许可，协调器停止全系统。这是独立的 CAN 链路问题，本次修改不屏蔽它，也不能靠取消升降归零解决。

## 源码与测试准备

- `control_manager` 删除停用时的升降 HOME 阶段及零位前提，直接在静止确认后返回双臂 home。
- `lift_adapter` 每收到新的完整反馈立即发布状态；反馈失效后也立即发布清空状态。错误分类和保护门槛保持不变。
- 启动参数、网页提示与使能判据同步更新。状态增加 `parking_policy=arms_home_lift_stopped`，不再声称任意高度的 home 已验证有支撑。
- 新增实际协调器加模拟设备的 5 项测试：短按 X 在非零高度归位并失能、等待升降停止/关闭会话、归位时升降移动、反馈丢失、B 停止保持。
- 升降虚拟 CAN 用例新增完整反馈及时发布检查。原有故障、握键、释放停止测试保留。
